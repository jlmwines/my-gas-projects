## Goal

Eliminate the 4 frequent race / stale-state issues in the Daily Sync widget so users don't see stuck buttons, missing stages, or buttons that fire too early. Make the UI a faithful mirror of the backend state at all times.

## Scope

In:

1. Generate web export button visible/clickable before the action can fire (orig 2026-01-28)
2. Export button stays visible after export step starts (orig 2025-12-29)
3. Sync widget doesn't show Comax product import stage when order export is skipped without a refresh (orig 2025-12-31)
4. Generate button stays after export completes — file generated and named, but button doesn't reset (orig 2026-03-17, distinct from 2026-03-03 stale-poll fix)

Out (deferred):

- Failed Comax import can't recover when corrected file is uploaded — rare case, separate plan.

## Architecture recap

- **Backend state** lives in one JSON object in SysConfig at `system.sync.state`, managed by `SyncStateService.js`. 12 stages + FAILED. Strict transition table at `SyncStateService.js:35-50`. Every backend action has a stage guard.
- **Frontend** is `AdminDailySyncWidget_v2.html` (single file, ~636 lines). One source of truth for the shared message/action area: `STAGE_CONFIG[stage]` lookup table at lines 164-179, rendered by `updateSharedArea()` at lines 236-281.
- **Polling** runs at 1s during spinner stages, 10s during waiting stages, off when IDLE/COMPLETE. See `adjustPolling()` at lines 576-606.
- **Action lifecycle** in `runAction()` at lines 385-458: disable buttons → spinner → backend call → success handler updates UI from returned state.
- **Race protection** today:
  - `actionInProgress` flag (line 157) — polls during an action skip the shared-area update (lines 542-557).
  - Strict-less-than stale-poll discard (lines 560-564) — the 2026-03-03 fix.

## Backend audit (read on 2026-05-05)

Confirmed by reading `WebAppSync.js` and `OrchestratorService.js`:

- **All user-triggered backend functions correctly transition AND return the post-state.** Specifically:
  - `importWebOrdersBackend` (`WebAppSync.js:123-190`): when `ordersToExportCount === 0`, sets stage = `WAITING_COMAX_IMPORT`, marks step3 'skipped', step4 'waiting', returns the post-state.
  - `exportComaxOrdersBackend` (`WebAppSync.js:201-264`): transitions through `EXPORTING_ORDERS` → `WAITING_ORDER_CONFIRM` (or `WAITING_COMAX_IMPORT` if empty), returns post-state.
  - `generateWebExportBackend` (`WebAppSync.js:389-430`): transitions to `GENERATING_WEB_EXPORT`, queues a job via `OrchestratorService.queueWebInventoryExport`, calls `OrchestratorService.run('hourly')`, returns. **Final transition out of GENERATING_WEB_EXPORT happens asynchronously via `_checkAndAdvanceSyncState`** (not by the backend function itself).

- **Polling endpoint `getSyncStateFromBackend` (`WebAppSync.js:17-23`) calls `OrchestratorService.checkAndAdvanceSyncState()` on every poll.** That means polling actively drives async stage advancement — the UI is the engine.

- **`_checkAndAdvanceSyncState` GENERATING_WEB_EXPORT branch (`OrchestratorService.js:1175-1230`) advances ONLY on terminal job statuses:**
  - `jobStatus === 'COMPLETED'` → `WAITING_WEB_CONFIRM` (or `COMPLETE` if no changes).
  - `jobStatus === 'FAILED' || 'QUARANTINED'` → `FAILED`.
  - **Any other status (`PENDING`, `PROCESSING`, `NOT_FOUND`, `ERROR`) → no transition.** Stage hangs at `GENERATING_WEB_EXPORT`. Spinner stays.

- **Job lifecycle (`OrchestratorService.js:621-680`):** queue creates `PENDING` row. `processPendingJobs` sets `PROCESSING` before calling the service. **Service is responsible for setting `COMPLETED`** itself — orchestrator only sets `FAILED` if the service throws.

- **Zombie killer exists (`OrchestratorService.js:567-601`):** any job stuck in `PROCESSING` for >15 minutes is marked `FAILED`. **But the zombie killer only runs inside `processPendingJobs`**, which is only called from `OrchestratorService.run(...)`. **Polling does NOT call `processPendingJobs`** — it only calls `_checkAndAdvanceSyncState`. So between hourly triggers, zombies aren't reaped.

- **`retryFailedStepBackend` (`WebAppSync.js:512-535`) sets stage = `failedAtStage` directly via `setSyncState` (not `transition`).** Doesn't validate. Doesn't re-queue jobs. So a failed async job + Retry only re-checks the job status; the export is not actually re-run.

### Bug 4: Generate button stays after export completes

**Confirmed root cause (cause #1):** the export job can finish its work (file written to Drive) but its row in SysJobQueue never reaches `COMPLETED`, leaving stage stuck at `GENERATING_WEB_EXPORT`.

How this happens:

1. User clicks Generate. `generateWebExportBackend` queues a `PENDING` job, calls `OrchestratorService.run('hourly')`, returns.
2. `processPendingJobs` picks up the job, sets `PROCESSING`, calls `ProductImportService.processJob(...)` (or whichever service runs the export).
3. Service writes the file to Drive successfully.
4. Service is about to write `COMPLETED` to the queue row, but Apps Script's 6-minute hard timeout fires first. Or service throws AFTER file write but before status update. Or any other path where the status update is skipped.
5. Status stays `PROCESSING`. File exists on Drive. Stage stuck at `GENERATING_WEB_EXPORT`.
6. Widget polls. `_checkAndAdvanceSyncState` reads job status = `PROCESSING`, doesn't advance. Spinner forever (or whatever the UI shows when stage = GENERATING_WEB_EXPORT).
7. **Zombie killer would catch this — but only when `processPendingJobs` runs, not on polls.** Until the next hourly trigger fires `OrchestratorService.run('hourly')`, the zombie sits.

This matches the symptom: "file is generated and named, but button doesn't reset". The user sees the file in Drive but the widget never advances.

The "Generate button" framing in the original report is likely loose terminology — the user means "the action area never returns to a clickable state" (still showing spinner from `GENERATING_WEB_EXPORT`). After up to 1 hour, the next hourly trigger reaps the zombie → status FAILED → widget shows Retry. User clicks Retry → stage returns to `GENERATING_WEB_EXPORT`, polls re-check the (now FAILED) status → widget shows Retry again. So even after the zombie kill, the widget cycles between Failed and Retry — never returning to Generate.

**Cause #2 (less likely but worth noting):** the same stuck-status pattern can happen earlier in the lifecycle (job stuck in `PENDING` because `processPendingJobs` didn't pick it up). Symptom would be identical — spinner stays.

**Fix candidates (in order of value):**

1. **Inline zombie check in `_checkAndAdvanceSyncState`** for the specific job being polled. If status is `PROCESSING` and `processed_timestamp` > N minutes old, mark `FAILED` right there. Catches stuck jobs on every poll, not just hourly. Lowest risk, highest value.
2. **Tighter zombie threshold for export jobs** — 6 minutes (Apps Script execution limit) instead of 15 minutes. The export can't legitimately exceed 6 minutes.
3. **Cross-check stage by file existence** — if `webExportFilename` is set on the state and the file exists in Drive, force-advance to `WAITING_WEB_CONFIRM` regardless of job status. Recovers from the file-written-but-status-not-set timing window without waiting for zombie kill.
4. **Make `retryFailedStepBackend` re-queue the failed job**, not just reset the stage — so retry actually re-runs the export instead of re-checking the same FAILED status.

### Bug 3: Comax import stage hidden after order export skip

**Reframed after backend audit.** `importWebOrdersBackend` correctly transitions to `WAITING_COMAX_IMPORT` and returns the post-state with `step3 = 'skipped'`, `step4 = 'waiting'`. The widget's `updateUI(status)` should render the "Import Comax" button immediately via `STAGE_CONFIG[WAITING_COMAX_IMPORT]`. **Backend is not the bug.**

Likely causes:

1. **A poll fires between the click and the success handler return** (10s idle interval, but action could take seconds). During the action, `actionInProgress = true` blocks shared-area updates. After the success handler returns, `actionInProgress = false`. The next poll reads stage = `WAITING_COMAX_IMPORT` and renders correctly. So the user *should* see the button. Unless the success handler itself isn't rendering — possible if `runAction` exited early.
2. **The user "without a refresh" description may mean within a brief invisible window.** Hard to confirm without repro.

**Verification:** repro on staging with a sync that has 0 orders to export. Click Import Orders. Open console, log every `updateSharedArea` call with `(stage, source)`. Determine whether the stage actually arrives in the success handler.

**Fix candidate:** TBD until repro. If the success handler does receive `WAITING_COMAX_IMPORT` and still doesn't render, the bug is in `updateSharedArea` or a CSS/DOM issue.

### Bug 2: Export button stays visible after export step starts

**Reframed after backend audit.** `exportComaxOrdersBackend` synchronously transitions through `EXPORTING_ORDERS` → `WAITING_ORDER_CONFIRM` and returns the post-state. So the success handler should never see stage = `WAITING_ORDER_EXPORT` post-click.

Plausible cause: a polling race during the action. `runAction` sets the spinner immediately. Polls during the action are blocked from updating the shared area. So the spinner should hold. UNLESS:

- The user clicked Export but the backend call hadn't yet started (network queue, Apps Script cold start). Polling fires, returns stage = `WAITING_ORDER_EXPORT`. But `actionInProgress` is true, so the poll skips the shared area. So the spinner from `runAction` stays.
- After the success handler runs and `actionInProgress = false`, the next poll fetches a fresh state. If the backend has fully advanced past `EXPORTING_ORDERS`, the new button (Confirm or Import Comax) renders. So no Export button.

**Most likely real cause:** the symptom may be misdescribed. The user may be seeing a brief moment during the action where the spinner doesn't replace the button cleanly (CSS layout shift, or the `disabled` state visible). Need staging repro to characterize.

**Verification:** record screen during a successful export-with-orders sync. Capture pixel-by-pixel what shows in the shared action area from click to confirm-button render.

**Live repro, 2026-08-27 (first one this plan has had for this family):** during Stage B's post-deploy sync test, clicking "Generate" (`WAITING_WEB_EXPORT`) left the button visibly unchanged on screen for the ~21s the export took to run inline — long enough that the user almost double-clicked it. No double-execution actually reached the backend (SysLog shows exactly one `generateWebExportBackend` call for the session), so no corruption occurred, but the UI symptom is real and specific: not a brief flash, a sustained stale render. Code trace found no explanation: `runAction` (`:377-395`) disables all buttons and replaces the action area with a spinner synchronously on click, before any network call starts; `refreshStatus`'s poll handler (`:570-604`) explicitly skips the action area while `actionInProgress` is true. Both mechanisms should have prevented this. Root cause is still open — needs browser console/DOM inspection live, not another blind code change.

**Root cause confirmed & fix designed, 2026-09-01 — the frontend was never the bug.** Second live occurrence: same symptom (Generate button visibly reappears mid-export), plus new corroborating fact — the user confirms that on a past occurrence they *did* click the reappeared button again, and it produced a genuine second export file. That rules out "cosmetic only" and confirms real double-submit risk. Static review of the backend (unchanged since 2026-08-27, even after Bug 5 Stage B's migration) found what browser inspection was never going to show, because the gap isn't client-side: **`generateWebExportBackend` (`WebAppSync.js:603-701`) never writes an intermediate processing stage before doing the work.** Its guard checks `WAITING_WEB_EXPORT` at the top, then `ProductService.exportWebInventory()` runs inline for the export's full duration (the 15-90s the SysLog timestamps show), and only afterward does its one `mutateSyncState` call flip the stage to `WAITING_WEB_CONFIRM`/`COMPLETE`. Shared state reads `WAITING_WEB_EXPORT` — button-visible, guard-passing — for the entire export. Any repaint that re-reads state mid-export (a second click after the widget re-renders, a second tab, a remounted view) legitimately sees `WAITING_WEB_EXPORT` and gets a live, guard-passing Generate button. Its two sibling actions in the same file don't have this gap: `startComaxImportBackend` (`:506-514`) and `pushWebInventoryBackend` (`:766-775`) each write their own `*ING_*` processing stage via `mutateSyncState` *before* starting the real work, closing the window immediately — a second call during either of those already fails the guard with `SyncStageStaleError`. `generateWebExportBackend` is the one action of the five missing that first write. This also fully explains the screen-lag complaint specific to this step (raised in the same 2026-09-01 report): no processing state exists for any poller to observe mid-export, so nothing on screen can move until the whole thing finishes, regardless of poll cadence — not a general polling-lag issue, unique to this one action.

**Fix design — mirror the two sibling actions exactly, no new mechanism:**

## Cross-cutting hardening

After fixing individual bugs, harden against the whole class of races:

1. **Stuck-stage detector.** The async pattern (`GENERATING_WEB_EXPORT` waiting on a job to flip to `COMPLETED`) has no timeout. If `_checkAndAdvanceSyncState` finds stage = `GENERATING_WEB_EXPORT` for > N minutes (say 10), advance to `FAILED` with a "stuck" error message. Same pattern likely applies to other async stages (`IMPORTING_PRODUCTS`, `IMPORTING_COMAX`, `VALIDATING`).
2. **Retry actually retries.** `retryFailedStepBackend` currently just resets the stage. For async-job stages, it should also re-queue the job. For synchronous-action stages, resetting the stage and letting the user click again is fine.
3. **Render gate in widget.** Shared message/action area is updated only by (a) the success handler from a fresh action, or (b) a poll whose `status.lastUpdated` is strictly newer than the last applied state. Track `lastAppliedTimestamp` separate from `lastActionTimestamp`.
4. **Stage assertion in success handler.** When an action expects specific post-transition stages, assert. Log a warning when the returned stage is unexpected — surfaces backend regressions immediately.
5. **Button-enable invariant.** Whenever a button is rendered into `#sharedAction`, set `disabled` based on `actionInProgress`. Today the disable is only on click-time (line 388); if a poll re-renders during an action, the new buttons are enabled by default.
6. **Single transition log.** Dev-only console log (`SyncWidget: stage <prev> → <new> via <source>`) so future race bugs are diagnosable from the browser console without instrumentation.

### Fix, finalized (2026-08-26, 3rd pass — exhaustive write-site migration)

**Supersedes the "corrected fix" this section held earlier today.** That version (lock only `_checkAndAdvanceSyncState`'s 3 branches + `exportWebInventory`) is itself incomplete: a full-repo audit (`grep -rn "SyncStateService\.\(setSyncState\|transition\|updateStep\)("`) found 15+ more writers of the same `system.sync.state` blob left unlocked, including `OrchestratorService.js#finalizeJobCompletion` (writes `archiveFileIds` mid-session, unlocked, confirmed at line ~913) and nearly every `WebAppSync.js` `*Backend` action function. **Locking a subset does not close the race** — an unmigrated writer still reads a stale unlocked snapshot and can clobber, or be clobbered by, a migrated writer's fresh locked state. A partial migration isn't a lower-risk version of this fix, it's a different and still-incomplete one — exactly the failure mode already seen twice (2026-08-25, first 2026-08-26 draft). Every write to `system.sync.state` must go through one locked primitive; no curated subset.

**Stage A — unchanged from §1.3.** Ship `LockHelpers.js#withScriptLock(context, timeoutMs, fn)` exactly as specced (`tryLock`, 30s timeout, log `lock-contention` + return `null` on contention, always release in `finally`). Smoke test; confirm `doGet`/`doPost` stay responsive while the lock is held. **Wait 24+ hours before Stage B** — this window de-risks the LockService mechanism itself (zero prior codebase precedent), not the migration.

**Stage B — exhaustive migration, shipped as one deploy (not split further — see rationale below).**
1. Add `SyncStateService.mutateSyncState(fn)`: acquire `withScriptLock`, re-read state fresh, call `fn(state)` to mutate in place, `setSyncState(state)`, release. **`fn`'s contract (reconciled with point 4 below, per 6th independent review, 2026-08-26 — the two were finalized separately and never explicitly tied together): `fn` mutates the fresh `state` object in place and returns normally to apply it, or throws `SyncStageStaleError` to signal "the guard I depend on no longer holds, abort."** `mutateSyncState` never catches that throw — it propagates to the caller (after releasing the lock). Its sibling `mutateSyncStateBestEffort(fn)` uses the exact same `fn` contract, but catches `SyncStageStaleError` specifically, logs it, and returns `{applied: false, state: <the fresh, unwritten read>}` instead of propagating — any OTHER exception `fn` throws (a genuine bug, not an expected staleness) propagates from both variants unchanged, never swallowed. On success, both variants return `{applied: true, state: <the written state>}` (`mutateSyncState` can be treated as always `applied: true` when it returns at all, since it throws instead of returning `false`). On lock contention (`withScriptLock` returns `null`): `mutateSyncState` throws a **dedicated `SyncLockContentionError`** — deliberately a different type from `SyncStageStaleError`, not a plain `Error` (7th independent review, 2026-08-26: a plain error here was indistinguishable from "a genuine failure" at the call site, causing contention to either spuriously mark a healthy sync FAILED or, if the recovery write also hit contention, silently swallow the error and reintroduce exactly the "click did nothing" symptom this whole primitive exists to prevent). **Its human-readable message ("The sync system is busy — please wait a moment and try again.") is set once, at construction, inside `mutateSyncState` itself — not left for a catch block to add later (9th independent review: found the message was only specified at a catch-block re-throw in point 4, so a first-write site with no surrounding `try`/`catch` at all — `skipToComaxBackend`, currently dead code with zero live callers, unflagged as such until now — would let a message-less error propagate raw to the frontend).** Every caller, whether it catches and re-throws or lets it propagate untouched, gets the same clear message for free. `mutateSyncStateBestEffort` returns `{applied: false, state: <a plain unlocked getSyncState() read>}` on contention, same as a guard mismatch — never throws. **`fn` must mutate the passed-in `state` object's own properties (`state.foo = x`) — never reassign `state` itself to a new object.** Any call site that today builds a brand-new object via `SyncStateService.getDefaultState()` — e.g. `const newState = SyncStateService.getDefaultState(); newState.sessionId = ...;` — rather than mutating a previously-read state falls into this trap if migrated literally: reassigning the local `state` parameter inside `fn` never touches the object `mutateSyncState` actually persists, silently no-op'ing the write with no error at all. **Check every call site of `getDefaultState()`, not a hand-picked subset (10th independent review, 2026-08-26: the 8th pass named only `importWebProductsBackend` and `apiPullAllBackend`, missing `SyncStateService.js#resetSyncState` — `const defaultState = getDefaultState(); setSyncState(defaultState);`, the same shape, reachable through `resetSyncStateBackend`, which point 4 below already commits to migrating).** `getDefaultState()` has exactly 5 call sites repo-wide (grep-confirmed) — the three that feed a write (`importWebProductsBackend`, `apiPullAllBackend`, `resetSyncState`) all migrate the same way: copy `getDefaultState()`'s fields ONTO the existing `state` reference (`Object.assign(state, SyncStateService.getDefaultState(), {...any per-call overrides})`), never declare a new local variable.

4. **Guard rule — one principle plus two mechanics needed to make it unambiguous (a 5th independent review, 2026-08-26, found the 4th pass's principle sound in outline but underspecified in two spots: (a) a function's `catch` block can be entered EITHER because write 1's own mismatch-check threw, OR because some unrelated real error happened after write 1 succeeded — the plan's prose only gave an example of the second case and generalized "every write after the first, including catch blocks" without saying how to tell the two apart, so a literal reading would wrongly no-op a genuine write-1 rejection instead of surfacing it; (b) `mutateSyncState` is built on `withScriptLock`, whose `fn` never runs at all on lock contention — the plan never said what a write-1 caller sees on contention, so under real polling load (which the plan itself says causes frequent contention) a genuine button-click could silently do nothing instead of throwing or succeeding. Both close below with explicit mechanics, not more prose.)**
   - **The governing distinction is still "does this write change `state.stage`,"** unchanged since the 3rd pass: a write that only touches other fields (`updateStep()`, `exportWebInventory`'s `webExportFilename`, `finalizeJobCompletion`'s `archiveFileIds`) needs locking only — re-read-inside-lock plus mutate-only-your-own-field means any concurrent `.stage` change already in the fresh read survives untouched. Confirmed correct by 3 independent reviews now — unchanged.
   - **Two `mutateSyncState` variants, chosen by whether "couldn't acquire the lock" and "guard already stale" should mean the same thing to the caller:**
     - **`mutateSyncState(fn)`** — for the very first stage-changing write in a function (`expectedCurrentStage` = the entry-guard stage). On lock contention, **throws** `SyncLockContentionError` (does not silently return). Inside the lock, if `state.stage !== expectedCurrentStage`, throws a dedicated `SyncStageStaleError` (not a generic `Error`) — a typed marker so the calling function's `catch` block can tell "I lost a race to a legitimate concurrent process," "the lock was simply busy," and "something actually broke" apart from each other. All three outcomes surface identifiably to the calling `catch` block, rather than a single generic throw the plan's own recovery logic could otherwise misclassify.
     - **`mutateSyncStateBestEffort(fn)`** — for every write after the first (a success-path "write 2," a catch-block write once write 1 is confirmed done, `_checkAndAdvanceSyncState`'s branches, and every non-stage-changing write). On lock contention OR a fresh-read guard mismatch, **silently no-applies** — logs a warning, returns the current true state, does not throw. Contention here means a concurrent process is already actively mutating this exact state; standing down is the same correct response as a mismatch, not a new case.
   - **`expectedCurrentStage` is reassigned, not fixed, across a function's execution — stated explicitly here because two prior reviews each found an unstated variant of this exact ambiguity:** it starts as the entry-guard stage for write 1. **The instant write 1's `mutateSyncState` call returns successfully, `expectedCurrentStage` is reassigned to the stage write 1 just set** (e.g. `exportComaxOrdersBackend`: starts `WAITING_ORDER_EXPORT`, becomes `EXPORTING_ORDERS` right after write 1 succeeds). Write 2 (and any catch-block recovery write) then compares the fresh read against THIS updated value, never the original entry stage — comparing against the original would make write 2 report stale on every normal, uncontended call, since write 1 already, correctly, moved the stage away from it.
   - **Catch-block disambiguation — three outcomes, not two, since a 7th independent review found "genuine failure" and "the lock was simply busy" were being conflated:** each function tracks one boolean, `write1Done`, set `true` only after its first `mutateSyncState(fn)` call returns without throwing. Its `catch (e)` block then does exactly one of three things — never a blind write:
     - **`e instanceof SyncStageStaleError`** (write 1 itself was rejected — by definition `write1Done` is still `false`): do **not** write anything. Log at info/warn ("lost the race to a concurrent process before this action began — no failure to record") and `return SyncStateService.getSyncState()`. A guard-mismatch is not a failure of *this* sync, so it must never produce a `FAILED` write — writing one here would itself be the clobber the whole fix exists to prevent.
     - **`e instanceof SyncLockContentionError`** (the lock itself was busy — this can happen whether or not `write1Done`, since the recovery write below acquires the lock too): do **not** write anything and do **not** treat it as a sync failure — nothing was learned about whether the action would have succeeded. Log at warn and re-throw the same `SyncLockContentionError` as-is — its message is already set at construction (point 1), not something this catch block needs to add. **Correction, 8th independent review:** `AdminDailySyncWidget_v2.html`'s `runAction()` failure handler (`:442-455`) has no type-based branching and no toast mechanism — it renders any thrown error identically, as red "Failed: `{err.message}`" text. There is no differentiated visual/semantic outcome here, and this plan doesn't add one (that would be a frontend-scope change). What actually differs for the user is the **message text alone** — "busy, please try again" instead of a stack-trace-flavored failure string — surfaced through the exact same generic rendering path a real failure uses. This is a smaller improvement than "distinct retryable outcome" implied, but an honest one: still strictly better than today's silent lost-update, not the richer UX the previous pass overstated.
     - **Any other error** (a genuine failure — network, code, data): write `FAILED` via `mutateSyncState(fn)` if `!write1Done` (acting as this execution's own first stage-changing write — re-checks the original entry guard, throws `SyncStageStaleError`/`SyncLockContentionError` per the same rules rather than double-failing something already resolved) or via `mutateSyncStateBestEffort(fn)` if `write1Done` (acting as a later write — checks the current `expectedCurrentStage`, no-applies silently on mismatch or contention). **This recovery write is itself wrapped in its own try/catch:** if it throws `SyncStageStaleError` or `SyncLockContentionError`, treat exactly as the two bullets above (no `FAILED` write, no spurious failure); if it throws anything else, `logger.error` both the original failure and this second one, and still `return SyncStateService.getSyncState()` — a `*Backend` function must never let an exception escape uncaught to the frontend, even when recording the failure itself fails. Follows the general `applied:false` → `reportFailure` rule below.
   - **General rule, and a completeness check keyed on the primitive's call site, not on the string `'FAILED'` (10th independent review, 2026-08-26: found two problems with the 9th pass's version — (a) grepping for the literal string `stage = 'FAILED'` has a real blind spot, `SyncStateService.js#transition()`, which sets `state.stage = newStage` with `newStage` as a variable, invisible to a content-based grep exactly the way `rebuildSysConfigFromSource`'s variable-key write defeated point 5's original gate; (b) the rule's "zero exceptions" framing collides with `_checkAndAdvanceSyncState`'s branches below, which correctly use the OPPOSITE polarity — this needed an explicit carve-out, not an implicit one a checker has to already know about):**
     - **Scope, precisely:** this rule applies to every `WebAppSync.js` `*Backend` function's `mutateSyncStateBestEffort` calls that write `stage = 'FAILED'` after a service call reports failure without throwing — check `applied`, and if `false`, fire `NotificationService.reportFailure` (`WebAppSync.js:428-434` precedent), because the write failing to apply means a real failure has nowhere else to surface. Known instances, illustrative only: `startComaxImportBackend:353-362`, `importWebProductsBackend:78-86`, `apiPullAllBackend:1008-1014`, `importWebOrdersBackend:143-151`, `exportComaxOrdersBackend:242-250`.
     - **Explicit carve-out, not an exception a checker has to infer:** `_checkAndAdvanceSyncState`'s three branches also call `mutateSyncStateBestEffort` for `FAILED` writes, but use the **opposite** polarity by design — gate `reportFailure` on `applied === true`, per point 205 below, because these are idempotent background pollers where only the execution that actually won the race should notify (the "genuine failure has nowhere else to surface" reasoning above doesn't apply — the failure DID get recorded, by whichever poller won). This rule and that one are deliberately different; a checker must treat `OrchestratorService.js#_checkAndAdvanceSyncState` as governed by point 205, not this bullet.
     - **The completeness check searches for calls to the primitive itself, `mutateSyncStateBestEffort(`, not for the string `'FAILED'`** — a fixed function name introduced by this migration, not spoofable via a variable the way the write's target value is. Post-migration, every live call site of `mutateSyncStateBestEffort(` (a finite, enumerable set, unlike "every place `stage` might end up `'FAILED'`") gets its `fn` body read to determine whether it can set `stage = 'FAILED'` (literal or via a variable/constant such as `STAGES.FAILED`) and, if so, which polarity applies per the two bullets above. (2) wrap the whole function (snapshot through restore, including `sheet.clear()` + `setValues()` over `getMasterConfiguration()`'s ~1700-row array) in one `withScriptLock` — this directly violates the plan's own cited locking discipline, `RELIABILITY_AUDIT.md` CCP-4: "scope to critical section only — never the full function (would burn 6-min budget inside the lock and starve other handlers including `doGet`/`doPost`)." A multi-second-to-double-digit-second script-wide lock during a routine deploy would queue or contend every migrated writer and every 1s widget poll for that whole window — the exact thing CCP-4 exists to prevent.

If it does **not** equal the default, something wrote real state during the window — skip the restore for that key (log a warning; leave the live write in place). No real writer ever produces either sentinel value (`"{}"` or `""`), so there's no false-positive "looks safe but wasn't" case. **The compare and the restore write happen inside the same lock hold, never released between them** (10th independent review: stated explicitly because a check-then-release-then-write implementation would reopen the exact TOCTOU window this fix exists to close, and would contradict §1.3's own lesson that a read-modify-write must happen *inside* the lock, not just have its write locked). Ten short, independent lock acquisitions (one per key, each a single read-compare-write) is the accepted cost, folded into the contention-volume accounting below, not a new full-function hold.

## Bug 6: Validation rule ERRORs are silently treated as pass, letting unvalidated data reach product/order masters

**Found 2026-08-26** while investigating whether Comax vintage changes could go undetected. Two separate questions, two separate answers: if the whole Comax import fails (throws), the master is safe — `_upsertComaxData` is never reached. But if the `comax_staging` suite runs to completion and one rule inside it throws (missing sheet/map, bad row data), that specific rule is recorded as `status: 'ERROR'` by `ValidationLogic.runValidationSuite`'s per-rule try/catch (`ValidationLogic.js:459-485`) — and nothing downstream treats `ERROR` as a reason to block. The suite as a whole still reports success, so the master upsert proceeds as if every rule had genuinely passed.

**Three independent places make this same "block or not" decision, and all three only check for `'FAILED'`, never `'ERROR'`:**
1. `ValidationOrchestratorService.processValidationResults` (`ValidationOrchestratorService.js:29-54`) — feeds `comax_staging`, `web_staging`, `web_xlt_staging` (`ProductImportService.js:346,744,230`; also 5 more `web_staging`/`web_xlt_staging` sites in `WooProductPullService.js:226-227,247-248,335-336,357-358,429-430`, all routed through the same function so they inherit the fix automatically) and `master_master` (via `processJob`, line 85, and the separate report-only periodic check at `HousekeepingService.js:708`).
2. `OrderService.js` web-order import (`OrderService.js:164`) — an independent inline check, `validationResult.results.some(r => r.status === 'FAILED')`, doesn't go through `processValidationResults` at all.
3. `WooOrderPullService.js` Woo API order pull (`WooOrderPullService.js:61`) — the same independent inline check.

An `ERROR` result is worse than a `FAILED` one, not milder — a `FAILED` result at least tells you what's wrong; an `ERROR` means the check never ran at all, so there's no way to know if the data is safe. Failing closed is correct.

**Fix — widen all three checks, no new mechanism needed:**
- `processValidationResults`: add `else if (result.status === 'ERROR')` alongside the existing `'FAILED'` branch — increment `failureCount` and force `quarantineTriggered = true` unconditionally, regardless of the individual rule's own `on_failure_quarantine` flag (a rule that never ran has no severity to honor). No new notification call needed: `master_master`'s caller (`processJob`, `ValidationOrchestratorService.js:94-100`) already fires `NotificationService.reportFailure` on any `quarantineTriggered`, and the three `ProductImportService.js` staging paths already log a CRITICAL `SysLog` line and set the job to `QUARANTINED` on any `quarantineTriggered` — both become correctly non-silent for free once the flag is set correctly.
- `_buildQuarantineErrorMessage` (`ProductImportService.js:52-71`) currently filters only `status === 'FAILED'` when building the human-readable quarantine message, so an ERROR-only quarantine falls through to a generic "Validation failed - data quarantined." string with no indication of which rule errored or why. Widen the filter to `status === 'FAILED' || status === 'ERROR'` and format `ERROR` entries using `result.message` (the caught exception text) instead of a discrepancy count, so the operator sees the actual cause.
- **A second, separate filter needs the same widening (independent review, 2026-08-26):** each of the three `ProductImportService.js` quarantine blocks (`:230-234` web_xlt, `:346-350` comax, `:744-748` web) logs `'CRITICAL: Quarantine triggered - MASTER UPDATE BLOCKED'` with a `validationFailures` metadata field built from its *own* inline `validationResult.results.filter(r => r.status === 'FAILED')` — distinct from `_buildQuarantineErrorMessage`'s filter, and not fixed by widening that function alone. If a quarantine is triggered solely by an ERROR, this metadata field would silently be `[]` even though the message string (post-fix) correctly names the cause. Widen this filter too, in all three call sites, to `r.status === 'FAILED' || r.status === 'ERROR'`.
- **`ContactService.js#runCrmValidation` (`:1013`, its own inline `.filter(r => r.status === 'FAILED')` at `:1021`) has the identical blind spot but is explicitly out of scope** — it only shapes a report surfaced via `AdminContactsView.html:1546`'s manual "run CRM validation" button, gating no master write. Noted, not fixed, so it isn't mistaken for an unverified gap: the scope-check item above was actually run (independent review, 2026-08-26) and this is the one other consumer it found.
- `OrderService.js:164` and `WooOrderPullService.js:61`: widen the condition to `r.status === 'FAILED' || r.status === 'ERROR'`. Both already log/throw visibly once triggered — no new visibility code needed there either.

**Scope check — done (independent review, 2026-08-26):** grepped every `ValidationLogic.runValidationSuite(` call site repo-wide. All route through `processValidationResults` except the two already named (`OrderService.js`, `WooOrderPullService.js`) and `ContactService.js#runCrmValidation`, a report-only path noted above as out of scope. No other independent decision-maker exists.

**Status: built 2026-08-27, not yet deployed.** All five sites widened to treat ERROR the same as FAILED: `ValidationOrchestratorService.processValidationResults` (new ERROR branch, unconditional quarantine), `_buildQuarantineErrorMessage` (widened filter, ERROR entries show the caught exception text instead of a discrepancy count), the 3 inline `validationFailures` log filters in `ProductImportService.js`, `OrderService.js:165`, `WooOrderPullService.js:61`. `ContactService.js#runCrmValidation` left as-is per scope note above. All touched files pass `node --check`.

### D1: No locking outside Bug 5's fix — job-queue pick-up and `ConfigService.setConfig`

**Load-bearing constraint, stated once here because it governs both fixes below and every future one (independent review, 2026-08-26, found the first draft violated it):** `withScriptLock` wraps `LockService.getScriptLock()` — **one single script-wide mutex, not a set of independently-named locks.** The `context` string passed to it is a log label only; GAS has no keyed/named locking primitive. Any code that acquires this lock must never call anything that tries to acquire it again in the same call stack — the lock is not reentrant, so a nested acquisition attempt hangs until its own timeout and then throws. This is why the first draft of the `setConfig` fix below was wrong, and it constrains how any future locked code in this codebase can be composed.

**`processPendingJobs`** (`OrchestratorService.js:606-684`) and **`processSessionJobs`** (`:1703-1809`) both read `SysJobQueue` for a `PENDING` row, then separately write `PROCESSING` to it — unlocked, and both target the same sheet, so they can race against each other, not just against themselves. This is `RELIABILITY_AUDIT.md` §1.3 Stage D's scope, just never built. The zombie-killer sweep earlier in `processPendingJobs` (`:566-598`) has the same unlocked read-then-write shape.

**Fix — two centralized locked primitives, reusing Bug 5's already-proven contract shape rather than inventing a new one.** Add to `OrchestratorService.js`, the file that already owns job-queue mechanics:
1. **`_claimNextPendingJob(jobQueueSheet, jobQueueHeaders, filterFn)`** — locked, re-reads fresh, finds the next row matching `filterFn` (all jobs for `processPendingJobs`, a specific `sessionId` for `processSessionJobs`) and marks it `PROCESSING`. **Return contract, three outcomes not two (5th independent review, 2026-08-26: two outcomes conflated "genuinely no jobs left" with "lock was contended, unknown," which matters for `processSessionJobs`'s stop-on-first-failure contract — a contended claim could otherwise be misread as "done"):** `{claimed: true, jobId, jobType, jobQueueSheetRowNumber}` on success; `{claimed: false, contended: false}` if a fresh scan genuinely found nothing matching; `{claimed: false, contended: true}` if the lock itself couldn't be acquired. **Retry bound made explicit, not "a few times" (6th independent review, 2026-08-26: unspecified retries risked unbounded blocking exactly in the high-contention 1s-polling scenario this fix targets, and diverged from Bug 5's own precedent — `mutateSyncState` throws immediately on contention rather than auto-retrying internally, pushing the retry decision to the caller).** `_claimNextPendingJob` itself uses a short per-attempt lock timeout (5s, not `mutateSyncState`'s 30s default — this is a hot, frequently-contended path, fail fast) and reports `contended: true` on the first failed attempt rather than looping internally. The caller retries at most 2 additional times, ~3s apart (matching the existing `WooInventoryPushService` auto-retry precedent already in this codebase — the 2026-08-25 incident fix, `WooInventoryPushService.js`'s own docstring, not Bug 4 as an earlier pass mis-cited — 14th independent review, 2026-08-26), then treats persistent contention as "nothing claimable this run" — for `processPendingJobs`, the outer loop/trigger cadence covers the next attempt; for `processSessionJobs`, this surfaces as a normal job-processing failure through its existing stop-on-first-failure path, not a silent "done."
2. **`setJobRowStatus(jobQueueSheet, jobQueueHeaders, jobId, fn)`** — **keyed by `job_id`, not row number (7th independent review, 2026-08-26 — see the `purgeOldJobs` finding below for why a row number isn't safe to hold across the unlocked work window).** Takes a mutator callback, not a static `updates` object (4th review: the static-object version serialized writes without stopping them clobbering each other — two reapers, or a reaper and a real completion, would each still unconditionally overwrite the row in turn, just one after another instead of concurrently). Locked, re-reads the sheet fresh, finds the row currently matching `jobId` (not a remembered row number), calls `fn(currentRowValues)` — `fn` returns the fields to write, or nothing/`undefined` to signal "don't apply, my precondition no longer holds" (including "row not found," treated the same as any other failed guard), exactly mirroring `mutateSyncState`'s `fn` contract. **`fn`'s guard is per-site, not one shared condition (5th review: the single "only if still PROCESSING" description was wrong for the one site not transitioning out of PROCESSING — see Phase 2 below).** Two variants, mirroring `mutateSyncState`/`mutateSyncStateBestEffort`:
   - **`setJobRowStatus` (must-apply):** for a job processor's own terminal write (real work already happened — a WooCommerce push, an import — so losing this write silently would misreport a job that actually succeeded, the same symptom class Bug 4 already fixed once). Same explicit retry bound as `_claimNextPendingJob` above (5s per-attempt timeout, up to 2 retries ~3s apart) before giving up; throws if still contended after that. **The throw must actually surface, not just avoid crashing anything (5th review found a real gap here — see below).** `fn`'s guard: only write if current status is still `PROCESSING`.
   - **`setJobRowStatusBestEffort`:** for the zombie sweep and `_reapStuckJobInSession` — opportunistic sweeps where "someone else already handled this row" is a normal, expected outcome. Silently no-applies on contention or a failed guard; `fn`'s guard: only mark `FAILED` if status is still `PROCESSING`, so a reaper can never overwrite a real, already-recorded `COMPLETED`. **`finalizeJobCompletion`'s Phase 2 unblock uses this same variant but a DIFFERENT guard** — it writes `BLOCKED → PENDING`, never touches `PROCESSING`/`FAILED` at all, so `fn` here checks "is status still `BLOCKED`," not the zombie-sweep guard above. **Confirmed low-priority in practice, precisely stated (6th independent review, 2026-08-26: the prior wording overclaimed):** grepped the entire codebase for the literal string `'BLOCKED'` — it appears in exactly one place, the read check inside Phase 2 itself (`OrchestratorService.js:935`); no `createJob` call site or anything else in the JS source ever writes that status. Phase 2's unblock logic is dead-by-code-path today (consistent with `.claude/bugs.md`'s existing note that `depends_on` enforcement was never actually wired up) — migrate it for consistency; the `BLOCKED`-check guard handles a real row correctly regardless of how it got there, so this precision doesn't change the fix, only the confidence claim around it.

This is exactly the "does this write change the thing I depend on" governing rule Bug 5's guard design already established — reused here for job rows instead of `system.sync.state`, not a new design.

**A real gap in how the must-apply throw actually reaches anyone (5th independent review, 2026-08-26) — the "propagates into the existing catch block, no new risk" framing was true but answered the wrong question.** Traced two real callers: `ProductImportService.js:1079-1082` and `OrderService.js:177-180` both call `_updateJobStatus(executionContext, finalJobStatus)` and then, **unconditionally on the local `finalJobStatus` variable** (not on whether the write actually landed), proceed to call `OrchestratorService.finalizeJobCompletion(...)` if it's `'COMPLETED'`. **`ConfigService.setConfig`** (`:228-267`) has the same unlocked check-then-write shape, general-purpose across every config key — not just `system.sync.state`. **The first draft wrapped `setConfig`'s own body in `withScriptLock` — this is wrong and would have broken Bug 5 outright**, not just D1: `SyncStateService.setSyncState` (`SyncStateService.js:97`) calls `ConfigService.setConfig` unconditionally, and Bug 5's `mutateSyncState`/`mutateSyncStateBestEffort` already hold the lock for the whole read-modify-write span that includes this call. Every single migrated sync-state write would try to re-acquire the lock it's already holding — hang for 30s, then throw, on every write, the moment D1 shipped.

**Corrected fix — two entry points, not one locked function:** leave `ConfigService.setConfig` itself unlocked (its current callers that are already inside a lock keep calling this raw version, unchanged). Add a new `ConfigService.setConfigLocked(settingName, key, value)` that wraps a call to the existing unlocked `setConfig` in `withScriptLock`, and migrate every general-purpose call site to call `setConfigLocked` instead. On contention, `setConfigLocked` throws a clear "could not acquire SysConfig lock" error — `setConfig` has dozens of callers with no shared expectation of a silent "write skipped" outcome, so failing loudly is the safer default, matching `mutateSyncState`'s write-1 contention behavior in Bug 5.

**A second already-locked caller, missed in the first draft (2nd independent review, 2026-08-26): `SetupConfig.js`'s `rebuildSysConfigFromSource` (templated in `generate-config.js`, both confirmed identical at the relevant line).** Bug 5 §5's finalized fix for this exact function requires its `RUNTIME_KEYS` restore loop's `ConfigService.setConfig(rk.name, rk.key, value)` call (`SetupConfig.js:91`) to run *inside* a lock hold that also covers the preceding compare-read ("the compare and the restore write happen inside the same lock hold, never released between them" — Bug 5 §5, above). A naive "migrate every general call site to `setConfigLocked`" sweep would catch this line too, since nothing in the code distinguishes it from an ordinary call site today — nesting `setConfigLocked`'s own lock acquisition inside Bug 5's already-held one, hanging then throwing on every `rebuildSysConfigFromSource()` run, i.e. every routine config deploy. **This call site must be explicitly excluded from the migration and keep calling the raw unlocked `setConfig`, exactly like `SyncStateService.setSyncState`** — both are noted here together so a future pass has one place to check, not two easy-to-miss exceptions.

**Status: passed independent review 2026-08-26, 15th pass, no findings — ready to build.** The longest review chain in this document (Bug 5 itself took 11 rounds). Rounds 1-14 each found and closed a real gap — a self-deadlock against Bug 5, missed already-locked callers, a growing list of unlocked `SysJobQueue` writers that only converged once reframed as one governing rule instead of an enumerated list, a write-clobber gap, an unreliable completeness check, a stale-row-number pattern that recurred five separate times before being generalized the same way, a variable-shadowing hazard, and a citation error — full trail above. Build order: this is downstream of Bug 5 (reuses its `withScriptLock`/`mutateSyncState` contract shapes directly) — Bug 5's Stage A and Stage B must ship first.

### D2: Sync-collision guard applied inconsistently

`performFrequentMaintenance` checks `SyncStateService.getActiveSession()` before its destructive writes (`HousekeepingService.js:592-603`); its sibling `performDailyMaintenance` does not, despite `archiveCompletedOrders` (`:1681-1902`), `purgeOldJobs` (`:2078-2157`), and `archiveCompletedTasks` all doing the same read-all→clear→rewrite pattern on sheets a sync can be actively writing to. `WooProductPullService.pullBundleProducts` (`:569-618`) does the identical unguarded full-sheet rewrite on `WebProdM`/`WebXltM`. This is the same defect class `RELIABILITY_AUDIT.md` §1.5 already scopes for `WebXltM`/`CmxProdM`/`SysProductAudit`'s *write-time* guard (don't write empty over populated) — D2 is the complementary *entry* guard (don't even start the destructive read-modify-write while a sync is active), and both should ship together since they defend against the same underlying collision from opposite ends.

**Correction (independent review, 2026-08-26): the third "already correctly guarded" sibling this section originally cited as a working example was itself broken and has now been fixed directly.** `WooProductPullService.refreshTranslationLinks` (`:406-417`) checked `syncState.currentStage` — but `SyncStateService`'s state object has a `.stage` field, never `.currentStage`, so the condition was always `undefined` and the guard never fired, for as long as this code has existed. Fixed (see git diff, `:408-410`) — this wasn't a copy-worthy precedent, it was a third live gap the original audit pass missed.

**Fix — two parts, since a naive "copy the same check" is wrong for `performDailyMaintenance` specifically (independent review, 2026-08-26):**
1. Extract `performFrequentMaintenance`'s existing check into a shared `_isSyncActive()` helper.
2. **`pullBundleProducts`** gets the straightforward version — call `_isSyncActive()` once at the top, before `_upsertBundleFieldsToMaster` runs, mirroring `performFrequentMaintenance`'s own whole-function-gate shape (the function does one thing).
3. **`performDailyMaintenance` must NOT be gated as a whole function** — confirmed on full read (`:666-821`) it runs ~20 unrelated subtasks (unit tests, schema validation, Mailchimp/coupon pulls, CRM intelligence, KPI recompute) alongside the three destructive ones. A whole-function gate would silently skip an entire day's worth of unrelated maintenance — tests, CRM, KPI — just because a sync happened to be active at trigger time, a materially worse failure mode than the guard is meant to prevent. Scope the check to wrap only `archiveCompletedOrders`, `purgeOldJobs`, and `archiveCompletedTasks` individually (or the block containing just those three), leaving the other ~17 subtasks unaffected by sync state.

§1.5's own scope line ("audited across all masters that use it, not just `WebXltM`") already commits to enumerating every clear-and-rewrite site — extend that same audit pass to confirm every one of them gets this entry guard, not just the sites found so far, so a fifth undiscovered gap isn't left exposed the same way these three were.

### D3: `RUNTIME_KEYS` (Bug 5, point 5) is hand-maintained and already stale — needs a build-time completeness check, not a bigger list

Adding the 10 currently-missing keys (`crm.pending_payment_followup.sent_order_ids`/`.floor_date`, `crm.frequent_pipeline.last_modified_floor`, `system.crm.welcome_floor_date`, `system.woocommerce.coupons_last_update`, `system.product_costs.last_recompute`, and 4 lower-severity cache keys) fixes today's drift but not the next one — nothing currently stops a future `ConfigService.setConfig` call site from writing a new runtime key without anyone remembering to register it. A **generic "preserve anything that differs from the master default" rule was considered and rejected**: `rebuildSysConfigFromSource`'s whole purpose is to make the live sheet match `config/*.json` exactly (its own docstring says so), so any row a `RUNTIME_KEYS`-style list doesn't cover is *supposed* to be wiped back to its shipped default on rebuild — a manual/stray edit to ordinary business config should not survive a rebuild. Preserving "anything that differs" would silently start keeping those stray edits too, a real behavior change beyond this bug.

**Fix — the same pattern as Bug 5's own completeness gates, applied here (confirmed workable, independent review 2026-08-26):** `generate-config.js` is plain Node (`require('fs')`/`require('path')`) with full filesystem access from the `jlmops` folder, and already builds the exact `(settingName, key, defaultValue)` data the check needs while generating `masterConfig` — grep the sibling `.js` source at generation time for every literal-string `ConfigService.setConfig(` **and, once D1 ships, `ConfigService.setConfigLocked(`** call site, extract each `(settingName, key)` pair, and fail the generation loudly if any resolved pair is covered by **neither** `RUNTIME_KEYS` **nor** a real (non-blank-placeholder) default already defined in `masterConfig`. Verified empirically against all 28 current call sites and all blank-default rows in `config/*.json`: every live case resolves correctly today, no false negatives.

**Two honest limitations, not fixed, stated so they aren't mistaken for covered (independent review, 2026-08-26):**
- **The literal-string blind spot is already live, not hypothetical.** `SyncStateService.js:97` calls `ConfigService.setConfig(SYNC_STATE_CONFIG_KEY, 'json', ...)` using a `const` variable for `settingName` — a naive grep/regex extraction can't resolve it. It happens to already be covered by `RUNTIME_KEYS` today (`system.sync.state` is in the list), so there's no live gap yet, but the check would silently pass this call site without actually verifying it, at the single highest-stakes call site in the whole plan.
- **Nothing enforces the invariant going forward.** A future setting shipped with a real non-blank default that later, in some other change, starts being written via `setConfig`/`setConfigLocked` at runtime would pass the check as "safe" (it has a real default) while actually needing `RUNTIME_KEYS` registration — the check catches missing keys, not a key silently changing category.

### D4: Widget's `retryFailed()`/`resetSync()` are near-duplicates of `runAction()` that drifted — missing its safety net, not differently designed

`runAction` (`AdminDailySyncWidget_v2.html:377-441`) arms a 2-minute safety timeout that force-clears `actionInProgress` and refreshes if the backend call never returns, and sets `lastActionTimestamp = status.lastUpdated` on success so a stale in-flight poll can't overwrite a fresh result. `retryFailed()` (`:514-534`) and `resetSync()` (`:536-564`) copy `runAction`'s `actionInProgress` guard and button-disable logic but never got either protection — confirmed on re-read, neither function references a timeout or `lastActionTimestamp` anywhere. Left as-is: a hung `retryFailedStepBackend()`/`resetSyncStateBackend()` call permanently blocks every future action (page reload is the only recovery), and a stale poll can revert a successful retry/reset back to the pre-action display.

**Fix — do not refactor `runAction` itself** (it already works, and it carries extra logic — step-card highlighting, business-level success/failure detection for the progress log — that doesn't apply to retry/reset and isn't worth the regression risk of touching). Instead, extract a small shared helper used only by `retryFailed`/`resetSync`, the two functions that are actually near-identical to each other: `_runManagedAction(rpcCall, {footerBusyText, footerDoneText, extraOnSuccess})` that owns the `actionInProgress` guard, button disable, arming/clearing a 2-minute timeout (mirroring `runAction`'s), and a standard success handler (`updateUI`, `adjustPolling`, `lastActionTimestamp = status.lastUpdated`, then `extraOnSuccess?.(status)`) and failure handler (reset `actionInProgress`, render the same Refresh-button fallback, prefix the error message). `retryFailed`/`resetSync` become thin callers passing their RPC name and the small bits that differ (reset's confirm dialog and progress-log clearing stay in `resetSync` itself, wrapping the call to the shared helper).

**Honest scope note (independent review, 2026-08-26):** this is a partial closure of the underlying defect class, not a full one — `runAction` still carries its own hand-maintained copy of the same timeout/`lastActionTimestamp` logic, so a future change to that shared contract (timeout duration, what counts as "done") still has to be updated in two places by hand, the same drift mechanism that produced this bug. Accepted tradeoff, stated explicitly rather than implied as fully solved: unifying all three into one helper would mean touching `runAction`'s step-card and business-success-detection logic too, which is the regression risk this fix deliberately avoids.
